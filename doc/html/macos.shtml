Native macOS

Slurm can run natively on macOS as a client, controller or compute node. Mac compute nodes support concurrent jobs, native process accounting and Metal GPU discovery. Optional task and process-tracking plugins provide the controls described under Accounting and enforcement.

Platform requirements

The initial target is macOS 26 on Apple Silicon. Intel Macs and older macOS releases require separate qualification; the CI matrix includes additional platforms to detect portability failures. Metal discovery uses macOS 10.15 APIs, which alone do not establish support for the complete port on that release. The optional private task policies require testing on each intended OS and GPU. See Testing.

Build and install

Use a native Apple compiler and macOS SDK, a C++ compiler, Perl, GNU Make, and Python 3 for the test scripts and documentation. Git checkouts also require Autoconf, Automake, GNU Libtool, pkg-config and the GLib aclocal macros. Regenerate from source inputs with autoreconf -fi; submit changes to configure.ac, macros and Makefile.am, following CONTRIBUTING.md.

Install MUNGE and the libraries needed by the selected plugins first. A package manager may provide these libraries, or they can be built into a site prefix. Use a MUNGE release with native macOS support, such as 0.5.18, and match its authentication configuration across the cluster.

The following example assumes that dependencies are installed together under /opt/slurm-deps. With separate package prefixes, pass each dependency's own prefix. Export PKG_CONFIG_PATH for Check, Lua and other libraries whose package metadata is outside the default search path. Shared libraries must also remain available at runtime.

# From a clean source checkout:
export CC=clang CXX=clang++
export ACLOCAL_PATH=/opt/slurm-deps/share/aclocal
autoreconf -fi
mkdir ../slurm-build
cd ../slurm-build
export PKG_CONFIG_PATH=/opt/slurm-deps/lib/pkgconfig
../slurm-source/configure --prefix=/opt/slurm \
  --with-munge=/opt/slurm-deps --with-hwloc=/opt/slurm-deps \
  --with-json=/opt/slurm-deps --with-yaml=/opt/slurm-deps \
  --with-lz4=/opt/slurm-deps --with-libhttp-parser=/opt/slurm-deps
make -j4
make install
# Optional contributed PMI client libraries and administration examples:
make -C contribs/pmi all install
make -C contribs/pmi2 all install
make -C contribs/macos install

Replace ../slurm-source with the actual source directory. Use a writable prefix for an unprivileged development installation. Normal multiuser service binaries, libraries and configuration must be administrator controlled. Configure detects Darwin plugin availability and linker behavior; it does not require GNU ld or objcopy to embed command help.

Run slurmrestd with a dedicated service account and group, separate from SlurmUser. A root-started service can use -u USER [-g GROUP] to clear supplementary groups before changing its group and user; omitting -g selects that user's primary group. The resulting account must retain access to its configuration, plugins and authentication credentials. Direct unprivileged startup requires an already suitable group list: supplementary groups must be empty or contain only the primary GID. Interactive macOS accounts commonly have additional groups and cannot remove them without privilege. Test authenticated REST requests with the selected account.

Compute node configuration

Install matching Slurm versions and feature-aware plugins on the controller, compute nodes and clients. Use consistent numeric user/group IDs, supplementary groups, authentication keys, clock synchronization, and resolvable hostnames. Provide matching working directories and application/data paths through shared storage or explicit staging. Applications and their dependencies must be built for each node's OS.

Run slurmd -C on each Mac and use its reported CPU topology. Choose RealMemory below physical memory to leave space for macOS, Slurm and other host services. Apple Silicon CPU cores can have different performance characteristics; their logical CPU count is not a throughput or performance-core guarantee. The following is an illustrative all-Mac compute configuration; replace its resources and paths with site values:

ClusterName=macs
SlurmctldHost=controller
SlurmUser=slurm
AuthType=auth/munge
CredType=cred/munge
SelectType=select/cons_tres
SelectTypeParameters=CR_Core_Memory
ProctrackType=proctrack/pgid
JobAcctGatherType=jobacct_gather/darwin
JobAcctGatherFrequency=task=5
TaskPlugin=task/darwin
NamespaceType=namespace/none
StateSaveLocation=/var/db/slurm/controller
SlurmdSpoolDir=/var/db/slurm/compute
NodeName=mac01 CPUs=8 RealMemory=14000 Feature=macos
PartitionName=mac Nodes=mac01 Default=YES MaxTime=01:00:00 State=UP

task/darwin requires darwin.conf beside the selected slurm.conf; an empty or comments-only file explicitly leaves native limits disabled. Copy share/slurm/macos/darwin.conf.example from the contributed installation to that directory as darwin.conf, then choose a site policy using darwin.conf(5). Keep the file and its parent directory administrator controlled. Use TaskPlugin=task/none if native task controls are not desired. Configless deployments must distribute the same darwin.conf.

Darwin uses /var/run for Slurm's runtime root (SLURM_RUN_DIR in the implementation); Linux retains /run. With auth/slurm, the default local credential sockets are /var/run/slurm/sack.socket, /var/run/slurmctld/sack.socket and /var/run/slurmdbd/sack.socket. Cluster-specific sackd directories also live under /var/run. These paths are independent of the installation prefix. The service must be able to create its correctly owned runtime directory; do not make the runtime root generally writable.

For configless slurmd, downloaded files remain in SlurmdSpoolDir/conf-cache. The local client discovery link is /var/run/slurm/conf, and the fallback configuration path is /var/run/slurm/conf/slurm.conf. Configure launchd explicitly rather than relying on a shell's environment. Test the selected authentication stack before admitting nodes to the cluster.

Darwin's configless and generated-script support uses owner-only temporary files named /tmp/slurm-memfd-XXXXXX, because macOS has no Linux memfd pathname namespace. Explicit cleanup and normal process exit remove files owned by the creating process; child cleanup preserves its parent's files. Replacing the owner with exec, using _exit, or a crash or SIGKILL can leave configuration or script content behind. Inspect ownership and confirm the owning Slurm process has stopped before removing residue; do not remove these files while a daemon or script may still use them.

Two jobs each requesting one CPU can run together when resources are available: for example srun -p mac -c1 --mem=256M sleep 30 in two terminals.

Mixed Linux/macOS clusters: TaskPlugin, ProctrackType, JobAcctGatherType and namespace settings are not partition-local controls. Adding a Mac partition does not make Linux cgroup settings usable on its nodes. Plan configuration/plugin compatibility for every daemon that reads the configuration, including a Linux controller. The Darwin plugins are built only on Darwin. A single unmodified global configuration selecting them is therefore not automatically a working mixed-OS configuration. Validate node-specific configuration delivery and controller plugin use end to end, or operate separate OS-specific Slurm clusters and use the existing federation mechanisms where appropriate.

Accounting and enforcement

Scheduler reservations control admission to a node. They do not impose hard aggregate CPU bandwidth or physical-memory quotas. Set application thread counts to the allocation and leave memory headroom for the operating system. Use node exclusivity when workloads need all resources on a host.

CapabilityDarwin behavior
CPU allocation and bindingConcurrent CPU allocations are supported. Explicit CPU/NUMA binding is rejected by task/darwin. A positive CoreSpecCount or a configured CpuSpecList rejects node initialization; CoreSpecCount=0 requires no specialization. Public affinity APIs do not provide Linux-style CPU binding or core-type placement.
Accountingjobacct_gather/darwin samples CPU time, RSS, virtual memory and available I/O, with process birth checks to detect PID reuse. Short-lived descendants and usage between samples can be missed. Final task wait/rusage supplements sampled totals. Shared pages can be counted more than once in summed RSS. Physical footprint, CPU frequency and unsupported counters are not exposed as accounting metrics.
Memory enforcementJobAcctGatherParams=OverMemoryKill can cancel jobs after observing excess usage. It cannot prevent allocation between samples. Missing measurements and process-discovery gaps affect this policy; see share/slurm/macos/resource-limits.md.
Task limitstask/darwin can lower per-process RLIMIT_CPU and RLIMIT_AS. Its optional initial-image footprint cap uses private spawn attributes, requires runtime/none and can reset on fork or subsequent exec. It is not a shared or task-lifetime RAM limit. See darwin.conf(5).
Process trackingThe default proctrack/pgid follows process-group membership; setsid or a group change can escape it. Optional proctrack/darwin retains observed descendants after detachment but can miss fast fork/exit/reparenting sequences. It reports detected cleanup failures and rejects wait-for-children. Neither backend provides containment for untrusted jobs. See share/slurm/macos/process-tracking.md.
External process adoptionAttaching an already running external PID to an extern step is unsupported, including with native policies disabled. Normal Slurm-launched tasks and their observed descendants can be tracked.
GPU accessMetal GRES scheduling and device selection are supported. Selection is advisory. An optional task policy denies new direct GPU connections to tasks with no allocated GPU; it uses deprecated/private Seatbelt interfaces and requires an empty remote SPANK stack. Existing or inherited capabilities and outside brokers remain usable. See Metal GPU support and darwin.conf(5).
Unsupported controlsHard aggregate CPU/RAM quotas, complete GPU isolation, GPU frequency control and per-job GPU memory/utilization/energy accounting are unavailable. Linux cgroup, namespace, task/affinity, procfs and energy plugins cannot be used on Macs.

The contributed installation includes detailed task, GPU and process-tracking guides in share/slurm/macos. Read them before enabling the optional native policies.

Service operation

contribs/macos supplies a renderer and launchd examples for slurmd, slurmctld and slurmdbd. They use absolute paths, explicit service users, foreground daemons, log files and bounded restart delays. Installation copies examples without activating them. Read their README before using launchctl bootstrap. Provision state/log directories and MUNGE first; launchd does not infer service readiness from these templates.

Use stable reachable node/controller addresses and permit the configured Slurm ports plus application traffic through host and network firewalls. Keep compute nodes awake while allocated: drain and wait for jobs before planned sleep, reboot, service removal or upgrades. A sleeping laptop is an unavailable node; configure power settings as part of node provisioning.

Before upgrades, drain nodes, preserve configuration/controller state, and follow the normal upgrade guide. Verify daemon registration, plugins and job completion before resuming nodes. Test crash, sleep and restart recovery with the intended workload, including cleanup of descendants that may leave process groups.

Testing

testsuite/macos/install-smoke.py checks an installed prefix without starting daemons. job-smoke.py runs jobs in a temporary same-user cluster with a private MUNGE instance. The optional --native-enforcement mode checks the initial-image footprint cap and GPU connection policy with supplied workload probes. The contributed share/slurm/macos/README.md gives build and invocation examples.

privileged-smoke.py tests root-to-worker UID/GID and supplementary groups, credentials, output ownership and cross-user job authorization. It requires root and an existing worker account. Its --self-check mode checks inputs and exits 77 without starting daemons or changing identity. The optional --native-enforcement mode also tests footprint kill/reset behavior and allocated/unallocated Metal access.

Both job harnesses require the first IPv4 address for the local hostname to resolve to loopback. They do not change name resolution or network settings. This restriction keeps their temporary clusters local; it is not a production cluster requirement. The Metal smoke test skips if no GPU is accessible, whereas enabling the GPU connection policy requires a successful hardware probe.

Test each deployment's OS, architecture, authentication, user identities and multi-node workloads before adding production nodes. Same-user tests do not exercise privileged user switching. PAM sessions, step-daemon crash recovery, sleep/reboot behavior, attached-GPU changes and optional database/JWT/TLS services need separate testing.
