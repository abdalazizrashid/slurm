Metal GPU scheduling on macOS

The gpu/metal plugin discovers Metal devices through Apple's public Metal framework. It records the GPU name and registry ID, and logs whether memory is unified and the recommended working-set size. The plugin requires macOS 10.15 or later. Build with an Objective-C compiler supporting ARC and the Foundation and Metal frameworks.

Configuration

Declare GPU resources in slurm.conf, using the count and optionally a substring of the normalized GPU name reported by slurmd -C: 

GresTypes=gpu
NodeName=mac01 Gres=gpu:1

Select discovery for the Mac in gres.conf:

NodeName=mac01 AutoDetect=metal

AutoDetect=full also probes Metal when available. slurmd -G checks the merged configuration. Do not specify File, MultipleFiles, Cores, Links, or CUDA/ROCm/oneAPI visibility flags for Metal devices. The plugin identifies devices by their Metal registry IDs, without device nodes or CPU affinity. Each device has a separate GRES bitmap bit. Both the controller and compute node must support identity-based GRES; older controllers cannot schedule these devices.

Applications and allocation

Request a device using the usual --gres=gpu:1 or --gpus=1 options. Slurm's GRES allocation prevents conflicting Slurm allocations of an exclusive device. It does not prevent other applications or jobs from opening that GPU through Metal.

SLURM_METAL_DEVICE_IDS contains comma-separated, zero-padded 16-digit hexadecimal registry IDs assigned to the job, step, or task. An application must use this list to select matching registryID values from MTLCopyAllDevices(); Metal does not interpret the variable or hide other devices. Slurm's usual SLURM_JOB_GPUS and SLURM_STEP_GPUS remain Slurm numeric indices. Do not interpret them as Metal enumeration order.

Map, mask and per-task GPU selection control the advisory assignment. Closest-CPU binding is unavailable because the plugin does not report GPU/CPU affinity. Frequency requests report GpuFreq=control_disabled. MPS and shard GRES configuration is rejected; MIG and driver-level GPU partitioning are unavailable.

Optional denial of unallocated GPU connections

With TaskPlugin=task/darwin, administrators can set DenyUnallocatedGPUConnections=yes in darwin.conf. This is disabled by default. It denies new direct GPU connections for local tasks whose authenticated job or step allocation has no GPU. GPU-allocated steps can still access all devices; per-task binding remains advisory.

The policy uses the deprecated/private Seatbelt profile interface. Enabling it requires the installed slurm-darwin-gpu-probe to demonstrate both successful Metal computation without the policy and denied direct device acquisition with it. Repeat this check after OS or GPU changes.

An empty remote SPANK stack is required for every step, including steps allocated GPUs. Optional and included plugin records are also rejected before loading. The restriction applies before task prologs and runtime initialization, and survives fork and exec. Task epilogs install the same policy before their executable or loader runs. Existing or inherited GPU capabilities remain usable, and outside IPC brokers can still perform GPU work. This does not provide selective-device authorization, GPU memory or time quotas, or complete device isolation.

See darwin.conf(5) for configuration and share/slurm/macos/gpu-access.md, installed from contribs/macos/gpu-access.md, for deployment requirements.

Memory and accounting

Unified memory is shared with the CPU. The working-set recommendation is a performance guideline, not dedicated VRAM, an allocation, or an enforced limit. GPU-count TRES allocation accounting is available. Per-process GPU memory, utilization and energy counters are unavailable.

Testing and operations

The test program testsuite/slurm_unit/common/metal-smoke runs a bounded compute kernel and verifies all results. It can run standalone or as srun --gres=gpu:1 /path/to/metal-smoke. Within a Slurm job it requires an assigned registry ID and fails if that device cannot be found.

Drain a node and finish its jobs before changing its attached GPUs. Test hot-plug and sleep/resume behavior before relying on them in production. Registry IDs identify devices across processes but may change after a reboot or hot-plug event. For general node configuration, see Native macOS support.
